# Liquidity and Migration Risks

A completed RugFreePump bonding-curve sale can transition into a Raydium CPMM liquidity pool.

Migration is an important lifecycle boundary because control moves from the bonding-curve sale environment into an external trading environment.

Liquidity migration therefore introduces both protocol-level and market-level risks.

## Migration is not an automatic guarantee

A completed sale does not mean that a successful external market has been created.

Migration is subject to protocol conditions and transaction execution.

The normal migration path requires, among other conditions:

- A finalized sale
- Required migration feature enablement
- Completion of the configured migration lock period
- No conflicting recovery or cancellation state
- No prior migration
- A valid authorized executor
- Valid Raydium program configuration
- Sufficient funds for required migration-related amounts

A sale can therefore be finalized without immediately becoming an externally traded market.

## Migration lock

The program applies a migration lock period after finalization.

The purpose of the lock is to prevent immediate migration before the configured delay has elapsed.

The exact duration is determined by the current protocol configuration.

## Who can execute migration

The normal migration operation can be executed by:

- The token creator, or
- The configured platform migration authority

Both paths remain subject to the program's validation rules.

An authorized migration executor cannot bypass the program's migration conditions.

## Raydium dependency

RugFreePump uses Raydium CPMM infrastructure for the external liquidity pool.

The program validates the expected Raydium CPMM program before invoking the external CPI.

Nevertheless, Raydium is an external protocol and remains outside RugFreePump's direct control.

Users therefore assume additional risks associated with:

- Raydium program behavior
- External account requirements
- Raydium availability
- Pool initialization
- External market activity
- Future external protocol changes

## Liquidity amount

The amount of liquidity available for migration depends on the finalized sale state and the deductions required by the protocol.

Applicable amounts can include:

- Configured completed-sale fees
- Creator incentive amounts where applicable
- DEX pool creation costs
- Required account rent
- Other protocol-defined migration requirements

The amount of liquidity ultimately placed into the external pool should therefore not be assumed to equal the total amount originally contributed to the bonding curve.

## Creator incentive

Where the protocol configuration enables a creator incentive, the migration process can allocate the configured creator incentive from eligible finalized-sale funds.

The creator incentive is calculated by the program according to the configured rules and is not an arbitrary amount selected during migration.

## LP token handling after migration

During normal liquidity migration, Raydium CPMM pool initialization returns LP tokens representing the liquidity position created by the migration.

The migration process burns those LP tokens and closes the associated LP token account.

As a result, RugFreePump does not retain those LP tokens as an ongoing protocol-controlled liquidity position after normal migration.

This describes the behavior of the current migration implementation. It does not eliminate market or liquidity risk and should not be interpreted as a guarantee about the future behavior of the external Raydium protocol.

## Migration and external market price

Creating a Raydium pool does not guarantee a particular token price.

Once liquidity becomes available externally, token price can change because of:

- Trading activity
- Market demand
- Arbitrage
- Liquidity depth
- Large trades
- Market-wide conditions
- Other external factors

A successful migration therefore does not guarantee that a token will retain its bonding-curve price.

## Post-migration liquidity risk

External liquidity can be limited.

A token may experience significant price impact when trades are large relative to available liquidity.

Users should distinguish between:

- The protocol's bonding-curve purchase calculation
- The liquidity available in the external market
- The market price after migration

These are different mechanisms.

## Migration transaction risk

Migration is an on-chain transaction involving multiple account relationships and an external CPI.

The transaction can fail if:

- Required accounts are incorrect
- Required funds are unavailable
- Migration conditions are not satisfied
- External program requirements are not satisfied
- The transaction exceeds execution requirements
- The sale has entered an incompatible state

Users should verify the confirmed migration transaction rather than relying only on the dApp interface.

## Migration state protection

The migration path uses an explicit in-progress state to prevent conflicting migration operations from being processed simultaneously for the same sale.

The program also prevents migration when incompatible recovery or cancellation states are active.

These controls constrain the lifecycle transition but do not eliminate external protocol or market risk.

## Emergency recovery

The program includes a finalized-sale recovery path for configured emergency situations.

When the required recovery mode and authority conditions are satisfied, finalized-sale liquidity can be handled through the administrative recovery path instead of normal Raydium migration.

Under this recovery path, the program transfers the applicable recovery funds and bonding-curve tokens to the authorized recovery authority according to the on-chain recovery rules.

Emergency recovery is therefore materially different from normal liquidity migration and should not be treated as an ordinary Raydium pool creation.

Users should inspect the on-chain sale state and transaction history when determining how a finalized sale was ultimately handled.

## Emergency cancellation

A finalized sale can also be canceled through the authorized emergency cancellation path when the required conditions are satisfied.

Emergency cancellation and finalized-sale recovery are distinct states, and the program prevents the two paths from being used simultaneously for the same sale under the relevant state checks.

A canceled finalized sale can become eligible for contributor withdrawals under the program's withdrawal rules.

## Terminal liquidity handling

Not every finalized sale should be described as having successfully migrated to an external trading pool.

The protocol records the resulting lifecycle state on-chain.

Depending on the circumstances, a finalized sale can result in:

- Normal Raydium migration
- Finalized-sale recovery
- Emergency cancellation followed by eligible withdrawals

Users should verify the actual on-chain state and transaction history rather than relying solely on the fact that the sale reached finalization.

## Post-migration token risk

Migration does not remove token-specific risks.

A migrated token can still:

- Lose value
- Become illiquid
- Experience extreme volatility
- Fail to attract trading activity
- Be affected by creator or holder behavior

Migration is a technical lifecycle transition, not a guarantee of project success.

## Current configuration

RugFreePump intends to retain the current protocol configuration for production unless the published configuration is explicitly changed.

Users should rely on the current protocol documentation and on-chain state rather than historical assumptions.

## User verification

After a sale reaches its migration stage, users can independently inspect:

- Sale state
- Migration transaction
- Raydium pool address
- Amounts recorded by the RugFreePump program
- External pool state

The on-chain record should be treated as the authoritative record of what actually executed.
