# Security Model

**RugFreePump** is a Solana-native token launch platform driven by an on-chain bonding-curve mechanism.

To reduce attack surface and establish clear security responsibilities, the protocol uses a compartmentalized security architecture that separates **core protocol execution** from the external systems and infrastructure that support it.

This model establishes explicit trust and security boundaries across the platform:

- **Core Execution Layer:** The **RugFreePump on-chain program** is the primary protocol execution layer. It enforces the rules implemented in the deployed program, performs the required on-chain calculations, validates state transitions and authorities, and records resulting protocol state directly on the Solana ledger.

- **External Security Boundaries:** The **Solana runtime**, oracle infrastructure, integrated third-party protocols, off-chain platform infrastructure, and end-user wallets operate as separate security domains with their own trust assumptions, failure modes, and operational responsibilities. RugFreePump validates external inputs and program interactions where applicable, but does not control these external systems.

This page explains how those boundaries work, what each component controls, and what trust assumptions remain.

<Note>
Security information describes the current RugFreePump architecture and operational model. It is not a guarantee that losses are impossible or that every component is free of vulnerabilities.
</Note>

## Security architecture

RugFreePump can be understood as several interconnected security domains.

### RugFreePump on-chain program

The RugFreePump on-chain program is the primary protocol execution layer.

It is responsible for enforcing the rules governing the core bonding-curve lifecycle, including:

- Creating token mints and bonding-curve sale state
- Maintaining sale state and contribution accounting
- Calculating bonding-curve purchases
- Applying configured protocol fees
- Enforcing purchase limits and sale conditions
- Processing eligible withdrawals
- Handling sale expiration, finalization, and cancellation states
- Enforcing liquidity migration conditions
- Validating relevant authorities and accounts
- Interacting with external on-chain programs where required

The program determines whether protocol operations satisfy the rules implemented in the deployed program and records the resulting state on Solana.

### Solana

Solana provides the blockchain execution environment in which RugFreePump transactions execute.

RugFreePump does not control:

- Solana network availability
- Transaction ordering
- Validator behavior
- Network fees
- Network-level failures or congestion

The resulting on-chain state depends on the deployed program, transaction inputs, account state, and Solana execution.

### Oracle infrastructure

Certain bonding-curve operations require SOL/USD conversion.

The current implementation uses Pyth price data and validates the supplied price before using it.

Pyth therefore represents an external security boundary. RugFreePump can validate the oracle data it receives according to its program rules, but it does not control the underlying oracle infrastructure or broader market conditions.

### External liquidity infrastructure

Completed sales can interact with Raydium CPMM infrastructure during liquidity migration.

Raydium is an external on-chain protocol that RugFreePump does not control.

The migration process therefore represents a separate execution boundary between the RugFreePump program and external liquidity infrastructure.

### Platform infrastructure

The RugFreePump website and supporting off-chain infrastructure provide the interface and information used by participants.

This includes services such as:

- Website infrastructure
- APIs and application services
- Indexing services
- Databases
- Real-time infrastructure
- Metadata infrastructure
- RPC providers
- Other supporting services

These services can affect availability or the information displayed to users, but they do not replace the on-chain program as the protocol execution layer.

An outage, indexing delay, or incorrect off-chain display does not by itself mean that the underlying Solana state has changed.

## Administrative trust model

RugFreePump is currently operated by a single authorized operator.

At the current stage of the project:

- The on-chain program is upgradeable.
- The founder/developer currently controls the program upgrade authority.
- Administrative and configuration authorities are currently controlled by the same operator.
- Maintenance controls are currently operated by the same authority.
- Critical administrative operations do not currently require multisig approval.
- There is no independent multisig governance layer currently deployed.

This is a fundamental part of the current security model.

A compromise or unauthorized use of the relevant administrative or upgrade authorities could therefore affect protocol behavior beyond the consequences of a normal user wallet compromise.

RugFreePump intends to introduce stronger governance controls in the future, including multisig authorization for critical operations. The on-chain architecture has been designed with support for this direction, but these future controls should not be treated as active protections today.

<Warning>
Do not assume that planned multisig governance, third-party custody, or other future security controls are currently protecting the protocol. The current security model is based on the authorities presently controlling the deployed system.
</Warning>

## On-chain security controls

The program contains state, account, and authority checks intended to constrain valid protocol operations.

Examples include:

- PDA derivation and account validation
- Sale-state validation
- Authority checks
- Maintenance-mode checks
- Sale expiration and finalization checks
- Migration lock periods
- Migration-state protection
- Validation of the expected Raydium CPMM program
- Oracle verification and freshness checks
- Purchase slippage checks
- Hard contribution limits
- Token supply and mint-authority controls

These controls define which state transitions the deployed program will accept.

They reduce the set of valid protocol operations but do not eliminate software, configuration, key-management, economic, or external-dependency risks.

## Token supply controls

When a token is created through RugFreePump, the current implementation creates a total supply of:

- 1,000,000,000 tokens
- 6 decimal places
- 800,000,000 tokens allocated to the bonding-curve sale
- 200,000,000 tokens allocated for liquidity

The mint authority is revoked after the initial token supply is minted.

This prevents the revoked mint authority from being used for later arbitrary token creation.

Token supply controls are a protocol-level property and should not be interpreted as a guarantee of token value, project quality, or market behavior.

## Oracle controls

The current purchase path validates the Pyth price update before using it.

The implementation currently requires:

- Full Pyth verification
- The expected SOL/USD feed
- A positive price
- A price update no older than 60 seconds
- Oracle confidence within the configured 2% threshold

These checks constrain the oracle data that can be accepted by the purchase path.

They do not eliminate the dependency on external oracle infrastructure or protect users from legitimate SOL price movements.

Detailed oracle-related risks are covered separately in [Oracle and Pricing Risks](/security-and-risk/oracle-and-pricing-risks).

## External protocol boundaries

Liquidity migration can interact with Raydium CPMM through an on-chain CPI.

RugFreePump validates the expected Raydium program before performing this interaction, but Raydium remains an external protocol outside RugFreePump's direct control.

Consequently, matters such as:

- Raydium program behavior
- External pool state
- Market liquidity
- Post-migration trading
- External market conditions

remain outside the RugFreePump security boundary.

Detailed migration risks and migration behavior are covered separately in [Liquidity and Migration Risks](/security-and-risk/liquidity-and-migration-risks).

## Off-chain information versus on-chain state

The RugFreePump dApp provides interfaces and information that help users interact with the protocol.

The website and supporting services should not, however, be treated as the ultimate authority for on-chain execution.

Users can independently inspect:

- Token addresses
- Program addresses
- Transaction signatures
- Account state
- Sale state
- Liquidity migration transactions
- Other publicly available Solana data

For significant transactions, users should verify the wallet prompt and resulting transaction rather than relying only on information displayed by the website.

## User wallet boundary

RugFreePump does not control user private keys or seed phrases.

The security of a user's wallet therefore remains a separate security boundary from the RugFreePump protocol.

A compromised wallet can result in loss independently of the security of the RugFreePump on-chain program.

Users are responsible for:

- Protecting wallet credentials
- Using the official RugFreePump domain
- Verifying transaction details
- Avoiding phishing websites
- Reviewing wallet prompts
- Keeping devices and browsers secure
- Confirming token and transaction addresses when appropriate

Detailed wallet and transaction risks are covered separately in [Wallet and Transaction Risks](/security-and-risk/wallet-and-transaction-risks).

## Security model in practice

RugFreePump's security model relies on separating protocol execution from the systems surrounding it.

The on-chain program determines whether protocol operations satisfy the implemented rules and records the resulting state on Solana.

The website and other off-chain services provide interfaces and supporting information, but they do not replace the on-chain execution layer.

Solana provides the execution environment, Pyth provides external price data for applicable operations, and Raydium provides external liquidity infrastructure for migration.

Users retain control of their own wallets and are responsible for approving transactions and protecting their wallet credentials.

No individual component should therefore be treated as providing complete security for the entire system.

## Current audit status

RugFreePump has not completed a formal third-party security audit at this time.

A professional security audit is planned for a future stage of the project.

Until an audit is completed and publicly documented, users should not interpret the existence of the public on-chain program or its published source code as equivalent to an independent security audit.

## Future security improvements

RugFreePump intends to strengthen the security model over time.

Planned improvements include:

- Multisig authorization for critical operations
- Additional separation of administrative responsibilities
- Third-party security review
- Formal security audit
- Additional operational security controls

These are future improvements and are not represented as active protections today.

## Independent verification

Users and developers can independently inspect RugFreePump transactions and on-chain state through Solana-compatible explorers and tools.

For the currently documented deployment and execution records, see the [Proof of Execution](/on-chain-program/proof-of-execution) page.

Security-related claims should always be interpreted according to the actual deployed program, authorities, configuration, and transaction history at the time of use.
