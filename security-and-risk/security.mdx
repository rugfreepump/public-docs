**RugFreePump** is a Solana-native token launch platform driven by an on-chain bonding-curve mechanism.

The protocol is designed around a clear separation between **on-chain execution and enforcement** and the external systems that provide application, data, and infrastructure services.

The most important security boundary is the RugFreePump on-chain program. Protocol rules, protocol state transitions, and protocol-controlled SOL and token movements are executed through the deployed on-chain program and Solana accounts rather than through the off-chain dApp.

The platform also depends on separate security domains, including Solana, Pyth, Raydium, off-chain infrastructure, and user-controlled wallets.

This page explains how these components interact, which controls are enforced on-chain, and which authorities and trust boundaries exist in the current deployment.

## Core security architecture

### On-chain protocol execution

The RugFreePump on-chain program is the primary protocol execution and enforcement layer.

The deployed program is responsible for the core protocol lifecycle, including:

* Token mint creation
* Bonding-curve sale creation and state management
* Contribution accounting
* Bonding-curve purchase calculations
* Protocol fee application
* Purchase and contribution limits
* Sale expiration and finalization
* Available withdrawals
* Liquidity migration
* Recovery and cancellation operations
* Required authority and account validation
* Interactions with required external Solana programs

Protocol operations are accepted only when the accounts, authorities, state, inputs, and conditions satisfy the rules implemented by the deployed program.

The resulting protocol state is recorded in Solana accounts.

### On-chain asset control

Protocol-controlled SOL and token movements are executed through the RugFreePump on-chain program and Solana accounts.

The off-chain RugFreePump infrastructure does not custody or directly control users' SOL or tokens.

The on-chain execution layer governs protocol-controlled asset operations including:

* SOL contributions to bonding-curve sales
* Token purchases
* Protocol fee transfers
* Available withdrawals
* Bonding-curve vault balances
* Liquidity migration
* Related protocol-controlled SOL and token transfers

The off-chain infrastructure, including the dApp, APIs, databases, indexers, and metadata services, does not directly execute or control protocol-controlled asset movements.

Off-chain application state therefore does not determine whether a protocol-controlled asset transfer is permitted.

The deployed RugFreePump on-chain program and the Solana runtime enforce the applicable rules and authorization requirements during transaction execution.

## On-chain security controls

RugFreePump uses account, state, authority, input, and lifecycle validation to constrain which protocol operations the deployed program will accept.

### Account and authority validation

The program validates the accounts and authorities required for each protocol operation.

Security-relevant controls include:

* PDA derivation
* Required account validation
* Authority validation
* Sale and account state validation
* Validation of accounts associated with the expected token and bonding-curve state
* Validation of required external program addresses

These checks prevent protocol instructions from simply operating against arbitrary accounts or unauthorized protocol state.

### Sale lifecycle controls

The program enforces the state transitions associated with a bonding-curve sale.

These controls include:

* Sale-state validation
* Purchase-condition validation
* Contribution limits
* Sale expiration checks
* Finalization conditions
* Migration eligibility checks
* Migration lock periods
* Migration-state protection
* Recovery and cancellation state validation

The program therefore determines which lifecycle transition is valid for the current on-chain state.

### Maintenance controls

RugFreePump includes an on-chain maintenance state that can restrict protocol operations when maintenance controls are enabled.

The program checks the maintenance state as part of operations that are restricted during maintenance.

The protocol also uses lifecycle conditions intended to prevent maintenance controls from being enabled while active bonding-curve sales are within their protected active lifecycle.

These checks are enforced by the on-chain program rather than by the dApp.

### Purchase protection

The bonding-curve purchase path includes controls intended to constrain accepted purchases.

These include:

* Minimum purchase requirements
* Contribution limits
* Purchase slippage validation
* Bonding-curve state validation
* Required SOL/USD oracle validation

These conditions are evaluated during on-chain transaction execution.

## Oracle security

The bonding-curve mechanism uses external SOL/USD price data because the curve is denominated and calculated using USD-equivalent values while buyers contribute SOL.

The current implementation uses Pyth price data and validates the supplied price before accepting it for protocol execution.

The purchase path currently requires:

* Full Pyth verification
* The expected SOL/USD price feed
* A positive price
* A price update no older than 60 seconds
* Oracle confidence is within the configured 2% threshold

These checks establish the conditions under which external price data can be accepted by the program.

RugFreePump controls the validation rules applied to the supplied oracle data but does not control the underlying Pyth infrastructure.

Pyth therefore remains an external security boundary.

## Token supply security

RugFreePump establishes a defined token supply during token creation.

The current implementation uses:

* Total supply: 1,000,000,000 tokens
* Decimals: 6
* Bonding-curve allocation: 800,000,000 tokens
* Liquidity allocation: 200,000,000 tokens

The initial supply is minted during token creation.

After the initial supply is created, the mint authority is revoked.

Once revoked, that authority cannot subsequently be used to create additional tokens.

This establishes the protocol's fixed-supply behavior for tokens created through the current token-creation flow.

### Liquidity migration security

Liquidity migration represents a controlled transition from the RugFreePump bonding-curve environment to Raydium CPMM liquidity.

The migration process is constrained by on-chain validation of the required sale state, timing, authorities, accounts, and external program.

### Raydium program validation

The RugFreePump program validates the expected Raydium CPMM program before performing the external interaction.

The migration therefore does not simply accept an arbitrary external program address supplied by an off-chain service.

The interaction with Raydium occurs through an on-chain CPI.

Raydium remains an external protocol and is outside RugFreePump's direct control.

### Migration state protection

The program tracks the migration state of a sale and validates whether migration is currently permitted.

Migration lock and state checks prevent conflicting migration-related operations from being accepted for the same sale.

This keeps the migration process within the state transitions defined by the RugFreePump program.

### Recovery path

RugFreePump includes a controlled recovery path for finalized sales when the normal liquidity-migration flow cannot safely complete.

Recovery provides an alternative on-chain handling path for exceptional finalized-sale conditions rather than requiring the protocol to remain permanently dependent on an unsuccessful normal migration attempt.

The recovery operation is restricted by the program's administrative authority and applicable on-chain state and account checks.

Recovery therefore acts as a protocol-level fallback mechanism for exceptional liquidity-migration conditions.

It does not bypass the on-chain program. The recovery operation itself must satisfy the authorization and state-transition rules enforced by the deployed program.

### Cancellation and contributor withdrawal

RugFreePump also provides a controlled cancellation path for finalized sales that cannot proceed through the normal liquidity-migration flow.

Cancellation transitions the sale into the applicable cancellation state under the conditions enforced by the on-chain program.

Once a finalized sale is placed into the cancellation state, contributors can use the protocol's withdrawal mechanism according to the applicable withdrawal rules.

This provides a defined on-chain exit path for contributor funds when a finalized sale cannot proceed through normal liquidity migration.

The cancellation mechanism is therefore a protocol-level safety mechanism that prevents a finalized sale from being dependent exclusively on successful completion of the normal migration path.

Cancellation and withdrawal remain governed by the deployed program, the sale's recorded state, contributor accounting, and the available balance in the bonding-curve vault.

### LP token handling

During successful liquidity migration, the LP tokens generated by the migration are automatically burned by the protocol flow.

The associated LP token account is then closed as part of the migration process.

This means the resulting LP position is not retained as an ongoing LP-token balance under the normal RugFreePump migration flow.

## Administrative authority and upgrade security

RugFreePump currently operates with a **single authorized authority** for the relevant program upgrade and administrative controls.

The current deployment includes:

* A single program upgrade authority
* A single authorized authority controlling the relevant administrative and configuration authorities
* Administrative controls governed by that authority
* No multisig requirement for critical administrative operations
* No independent multisig governance layer currently deployed

This single-authority model is a fundamental security assumption of the current deployment.

### Program upgradeability

The RugFreePump on-chain program is upgradeable.

The current program upgrade authority is controlled by the authorized authority described above.

An authorized program upgrade can therefore change the code governing protocol execution.

Program upgrade authority is consequently part of the protocol's security boundary and must be protected accordingly.

### Administrative controls

The authorized administrative authority controls the protocol-level administrative functions implemented by the deployed program.

These can include maintenance, configuration, recovery, cancellation, and other restricted protocol operations where applicable.

Administrative authority does not come from the off-chain backend or database. It is enforced through the authorities and account checks implemented by the on-chain program.

Future security improvements may introduce additional authorization layers, including multisig control.

Such mechanisms are not considered active protections until they are actually deployed and used by the protocol.

## External security boundaries

RugFreePump depends on external systems that are outside its direct control.

### Solana

Solana provides the blockchain execution environment and account model in which the RugFreePump program operates.

RugFreePump does not control:

* Solana validators
* Transaction ordering
* The Solana runtime
* Network-level execution
* The broader Solana network

The RugFreePump program executes according to the Solana transaction, account, and program execution model.

### Pyth

Pyth provides the external SOL/USD price data required by the bonding-curve mechanism.

RugFreePump validates the supplied price according to its program rules but does not control the underlying oracle infrastructure.

### Raydium

Raydium provides external liquidity infrastructure used during migration.

RugFreePump validates the expected Raydium program before interacting with it, but Raydium remains an independent external protocol.

## Off-chain security boundary

The RugFreePump dApp and supporting off-chain infrastructure provide application and information services.

These systems include:

* Website and dApp infrastructure
* APIs and application services
* Blockchain indexing
* Databases
* Real-time infrastructure
* Metadata infrastructure
* RPC providers
* Other supporting platform services

These systems can present information, retrieve indexed blockchain data, prepare supported transactions, provide metadata, and deliver real-time updates.

They do not replace the RugFreePump on-chain program as the authority for protocol state transitions or protocol-controlled asset movements.

The off-chain database is therefore not the authoritative ledger for protocol-controlled SOL, tokens, or on-chain protocol state.

The resulting Solana account state and transaction execution remain authoritative for on-chain protocol operations.

## User wallet security boundary

User wallets are separate from the RugFreePump protocol.

RugFreePump does not control:

* User private keys
* Seed phrases
* Wallet signing authority
* User wallet balances

Transactions requiring user authorization must be approved by the user's wallet.

Users therefore retain control over the signing authority associated with their wallets.

The wallet boundary is separate from the administrative authority of the RugFreePump protocol.

## Independent on-chain verification

RugFreePump protocol execution can be independently inspected through Solana-compatible explorers and tools.

Publicly verifiable information includes:

* RugFreePump program addresses
* Token mint addresses
* Solana account state
* Transaction signatures
* Program instructions
* Sale state
* Protocol-controlled account activity
* Liquidity migration transactions
* Resulting blockchain state

The blockchain provides the authoritative record of executed protocol transactions and resulting on-chain state.

The dApp therefore does not need to be treated as the sole source of truth for protocol execution.

For the currently documented deployment and execution records, see the [Proof of Execution](/on-chain-program/proof-of-execution) page.

## Current audit status

RugFreePump has not completed a formal third-party security audit at this time.

A professional security audit is planned for a future stage of the project.

The availability of the on-chain program or its published source code does not constitute an independent security audit.

## Future security improvements

RugFreePump intends to strengthen the security architecture over time.

Planned improvements include:

* Multisig authorization for critical operations
* Additional separation of administrative responsibilities
* Third-party security review
* Formal security audit
* Additional operational security controls

These are future improvements and are not represented as active protections in the current deployment.

## Security model summary

RugFreePump's security model is built around a clear separation of authority and execution.

The **RugFreePump on-chain program** is the primary enforcement layer for protocol rules, state transitions, and protocol-controlled asset movements.

**Solana accounts and the deployed program** provide the execution environment for those operations.

**Off-chain infrastructure** provides application and information services but does not serve as the authoritative execution layer or as a custodian of users' SOL or tokens.

**Pyth** provides externally sourced SOL/USD data that is validated by the program.

**Raydium** provides external liquidity infrastructure that is validated and accessed through the on-chain migration flow.

**User wallets** remain under user control and provide the signing authority for user-approved transactions.

The current deployment also relies on a **single authorized authority** for program upgrades and relevant administrative controls.

Together, these boundaries define the current security model of the deployed RugFreePump system.
