RugFreePump exposes its public on-chain interface through an Anchor program.

The published Anchor IDL provides the machine-readable description of the program interface. Generated TypeScript types provide compile-time support for TypeScript integrations.

The IDL and generated types are version-specific and must correspond to the deployment being integrated with.

## Published resources

The Developer Guide repository contains:

```text
developer-guide/anchor-idl-and-types/resources/rug_free_pump.json
developer-guide/anchor-idl-and-types/resources/rug_free_pump.ts
```

Use the artifacts corresponding to the program deployment you are integrating with.

The current documented Devnet program ID is:

```text
9hpBPEiywp7FPAq5uP253eAZzdJ1Cpd36L5RAYuc9xSw
```

The Mainnet program ID must be replaced after Mainnet deployment.

## What the IDL provides

The Anchor IDL describes the program interface, including:

* Instructions
* Instruction arguments
* Account requirements
* PDA relationships
* Account types
* Events
* Program metadata
* Defined types

For the currently supported developer integration surface, the relevant public instructions are:

```text
buy(...)
withdraw()
```

The complete account and validation requirements for those instructions are documented separately:

* [Buy](../on-chain-integration/buy)
* [Withdraw](../on-chain-integration/withdraw)

The IDL is the machine-readable representation of the deployed program interface.

## Installing client dependencies

A TypeScript application can use standard Anchor, Solana Web3.js, and SPL Token libraries.

```bash
npm install @coral-xyz/anchor @solana/web3.js @solana/spl-token bn.js
```

Use dependency versions compatible with the Anchor interface and your application.

## Loading the IDL

A read-only Anchor program client can be created without a wallet:

```ts
import {
  AnchorProvider,
  Idl,
  Program,
} from "@coral-xyz/anchor";

import {
  Connection,
} from "@solana/web3.js";

import rugFreePumpIdl from "./rug_free_pump.json";

const connection =
  new Connection(
    process.env.SOLANA_RPC_URL!,
    "finalized",
  );

const provider:
  Omit<AnchorProvider, "wallet"> = {
    connection,
    opts: {
      commitment: "finalized",
    },
  };

const program =
  new Program(
    rugFreePumpIdl as Idl,
    provider,
  );
```

This read-only client can be used to fetch protocol accounts and inspect state.

A transaction-signing application should configure an `AnchorProvider` with its own wallet.

## Read-only account access

A wallet is not required to inspect protocol state.

For example:

```ts
import { PublicKey } from "@solana/web3.js";

const PROGRAM_ID = new PublicKey(
  process.env.RUG_FREE_PUMP_PROGRAM_ID!,
);

const mint = new PublicKey(
  MINT_ADDRESS,
);

const [bondingCurvePda] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("bonding-curve"),
      mint.toBuffer(),
    ],
    PROGRAM_ID,
  );

const bondingCurve =
  await program.account.bondingCurvePda.fetch(
    bondingCurvePda,
  );

console.log({
  active: bondingCurve.isSaleActive,
  finalized: bondingCurve.isSaleFinalized,
  expired: bondingCurve.isSaleExpired,
  totalRaisedUsdE2:
    bondingCurve.totalRaisedUsdE2.toString(),
  totalSoldTokensE6:
    bondingCurve.totalSoldTokensE6.toString(),
});
```

Use the current on-chain account state when making protocol decisions.

## Reading global state

The global state account is derived from:

```text
["global-states"]
```

Example:

```ts
const [globalStatesPda] =
  PublicKey.findProgramAddressSync(
    [Buffer.from("global-states")],
    PROGRAM_ID,
  );

const globalStates =
  await program.account.globalStatesPda.fetch(
    globalStatesPda,
  );

console.log({
  buyFeeBps:
    globalStates.buyFeeBps.toString(),
});
```

The `buy` instruction reads `buyFeeBps` from `GlobalStatesPDA`.

Do not assume every value present in a configuration account is necessarily consumed by every instruction. Refer to the specific instruction documentation for the source of each value.

For `buy`, the current minimum purchase and maximum raise are enforced by program constants, while the buy fee is read from global state.

## Generated TypeScript types

The generated TypeScript file provides types corresponding to the Anchor program.

Use generated types where they improve compile-time safety for:

* Account data
* Program structures
* Events
* Instruction clients
* Defined protocol types

Generated types do not replace the deployed program's actual state.

The following must correspond:

```text
Program ID
    +
IDL version
    +
Generated types
    +
Deployed program
```

Do not combine an IDL or generated type file from one deployment with a different deployed program version.

## Building an instruction

Anchor can construct an instruction without immediately sending it.

For example:

```ts
const instruction =
  await program.methods
    .withdraw()
    .accounts({
      buyer,
      adminStatesPda,
      mint,
      bondingCurvePda,
      bondingCurveVault,
      buyerAccumulationPda,
      buyerAssociatedTokenAccount,
      tokenProgram: TOKEN_PROGRAM_ID,
      systemProgram:
        SystemProgram.programId,
    })
    .instruction();
```

The resulting instruction can be placed into a transaction constructed by the integrating application.

This is useful when an application needs to:

* Add compute-budget instructions
* Add a priority fee
* Combine multiple instructions
* Build a versioned transaction
* Use a custom transaction pipeline
* Submit through custom RPC infrastructure

## Sending a transaction

An Anchor wallet provider can submit the instruction directly:

```ts
const signature =
  await program.methods
    .withdraw()
    .accounts({
      buyer,
      adminStatesPda,
      mint,
      bondingCurvePda,
      bondingCurveVault,
      buyerAccumulationPda,
      buyerAssociatedTokenAccount,
      tokenProgram: TOKEN_PROGRAM_ID,
      systemProgram:
        SystemProgram.programId,
    })
    .rpc();

console.log(signature);
```

For `buy`, always fetch fresh bonding-curve state before constructing the instruction because the expected state values form part of the protocol's slippage protection.

## Integer handling

Protocol values should be handled as exact integers.

Prefer:

* `BN`
* `bigint`
* Another exact integer representation

for:

* Lamports
* Token e6 amounts
* USD e2 amounts
* Basis points
* Large counters
* Unix timestamps when arithmetic is required

Example:

```ts
const lamportsAmount =
  new BN("100000000");
```

represents:

```text
0.1 SOL
```

without converting the financial amount through floating-point arithmetic.

## Reading large account values

Anchor account values representing large integers should be converted explicitly before arithmetic.

For example:

```ts
const totalRaisedUsdE2 =
  BigInt(
    bondingCurve.totalRaisedUsdE2.toString(),
  );

const totalSoldTokensE6 =
  BigInt(
    bondingCurve.totalSoldTokensE6.toString(),
  );
```

This avoids accidental precision loss when values exceed JavaScript's safe integer range.

## PDA derivation

PDAs must use the exact seeds defined by the on-chain program.

### Bonding curve

```ts
const [bondingCurvePda] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("bonding-curve"),
      mint.toBuffer(),
    ],
    PROGRAM_ID,
  );
```

### Bonding-curve vault

```ts
const [bondingCurveVault] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("bonding-curve-vault"),
      mint.toBuffer(),
    ],
    PROGRAM_ID,
  );
```

### Buyer accumulation

```ts
const [buyerAccumulationPda] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("buyer-accumulation"),
      bondingCurvePda.toBuffer(),
      buyer.toBuffer(),
    ],
    PROGRAM_ID,
  );
```

The buyer accumulation PDA uses the bonding-curve PDA as a seed component.

Do not substitute the mint.

### Admin states

```ts
const [adminStatesPda] =
  PublicKey.findProgramAddressSync(
    [Buffer.from("admin-states")],
    PROGRAM_ID,
  );
```

### Global states

```ts
const [globalStatesPda] =
  PublicKey.findProgramAddressSync(
    [Buffer.from("global-states")],
    PROGRAM_ID,
  );
```

### Platform fee vault

For `buy`:

```ts
const [platformFeeVault] =
  PublicKey.findProgramAddressSync(
    [Buffer.from("platform-fee-vault")],
    PROGRAM_ID,
  );
```

## Events

RugFreePump emits Anchor events including:

```text
BuyCompleted
BondingCurveSaleFinalized
BondingCurveSaleExpired
WithdrawCompleted
```

Events are useful for:

* Indexing
* Analytics
* Activity feeds
* Transaction interpretation
* Off-chain notifications

Events should not be treated as a replacement for current account state when an integration needs authoritative protocol state.

For example, a client can observe `BuyCompleted` but should still read the `BondingCurvePDA` when it needs the current sale state.

## Buy integration sequence

A production `buy` integration should:

```text
1. Determine the target deployment.
2. Load the matching IDL.
3. Derive required PDAs.
4. Read current BondingCurvePDA.
5. Read current totalRaisedUsdE2.
6. Read current totalSoldTokensE6.
7. Select the gross SOL amount.
8. Select slippage tolerance.
9. Supply the correct Pyth SOL/USD account.
10. Build the buy instruction.
11. Sign as the buyer.
12. Submit and confirm.
13. Refresh protocol state.
```

See [Buy](../on-chain-integration/buy) for the complete specification.

## Withdraw integration sequence

A production `withdraw` integration should:

```text
1. Determine the target deployment.
2. Load the matching IDL.
3. Derive required PDAs.
4. Read current BondingCurvePDA.
5. Read BuyerAccumulationPDA.
6. Derive the buyer token ATA.
7. Build the withdraw instruction.
8. Sign as the buyer.
9. Submit and confirm.
10. Read the resulting state and transaction data.
```

See [Withdraw](../on-chain-integration/withdraw) for the complete specification.

## Direct Solana integration

Anchor is not mandatory.

A developer can construct Solana instructions directly if the application correctly implements:

* Anchor instruction discriminators
* Argument serialization
* Account metas
* PDA derivation
* Program IDs
* Account layouts
* Required signer relationships
* Required validation assumptions

The published IDL and generated types make standard Anchor integrations easier, but the underlying protocol remains a Solana program.

## Versioning

The IDL is version-specific.

When updating an integration:

1. Confirm the target program ID.
2. Obtain the IDL corresponding to that deployment.
3. Update generated types.
4. Revalidate PDA derivation.
5. Revalidate instruction accounts.
6. Revalidate instruction arguments.
7. Re-test transaction construction.
8. Re-test event decoding.
9. Revalidate protocol configuration assumptions.

Do not assume that a change to RugFreePump's hosted application represents an on-chain protocol change.

Likewise, do not assume that an on-chain program change is reflected immediately in an internal application implementation.

## Public integration boundary

The public developer interface is the deployed RugFreePump on-chain program and its documented:

* Instructions
* Accounts
* PDAs
* Events
* IDL
* Generated types
* Required external protocol accounts

RugFreePump's internal backend, database, HTTP endpoints, WebSocket infrastructure, and transaction-builder classes are application infrastructure rather than required protocol dependencies.

## Future developer tooling

RugFreePump plans to provide:

* A maintained CPI wrapper
* A Rust integration crate

These tools are intended to simplify program-to-program integration while preserving the underlying on-chain protocol interface.

No public off-chain SDK or hosted developer API is currently part of the RugFreePump developer surface.
