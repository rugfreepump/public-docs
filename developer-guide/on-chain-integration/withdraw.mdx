---
title: "Withdraw"
description: "Integrate directly with the RugFreePump withdraw instruction to redeem a buyer's recorded contribution after a sale becomes withdrawable."
---

The `withdraw` instruction allows a buyer to redeem their recorded contribution after a RugFreePump sale is no longer active and the protocol's withdrawal conditions are satisfied.

The instruction has no arguments.

During a successful withdrawal:

1. The protocol performs a lazy expiration check when necessary.
2. The buyer's recorded net contribution is read.
3. Any remaining RugFreePump sale tokens in the buyer's ATA are burned.
4. The buyer's token ATA is closed.
5. SOL is transferred from the bonding-curve vault to the buyer.
6. The buyer's accumulation PDA is closed and its recoverable rent is returned.
7. `WithdrawCompleted` is emitted.

The buyer is the required signer and transaction payer.

## Instruction

```rust
pub fn withdraw(
    ctx: Context<Withdraw>,
) -> Result<()>
```

There are no instruction arguments.

The withdrawal amount is determined entirely from current on-chain state.

## Accounts

| Account                       | Mutable | Signer | Derivation / requirement                                                                   |
| ----------------------------- | ------- | ------ | ------------------------------------------------------------------------------------------ |
| `buyer`                       | Yes     | Yes    | Buyer receiving the SOL refund.                                                            |
| `adminStatesPda`              | No      | No     | PDA: `["admin-states"]`.                                                                   |
| `mint`                        | Yes     | No     | Token mint. Must match `bondingCurvePda.tokenMintAddress`.                                 |
| `bondingCurvePda`             | Yes     | No     | PDA: `["bonding-curve", mint]`.                                                            |
| `bondingCurveVault`           | Yes     | No     | PDA: `["bonding-curve-vault", mint]`.                                                      |
| `buyerAccumulationPda`        | Yes     | No     | PDA: `["buyer-accumulation", bondingCurvePda, buyer]`. Closed after successful withdrawal. |
| `buyerAssociatedTokenAccount` | Yes     | No     | Buyer's ATA for the sale token. Must exist. Tokens are burned and the ATA is closed.       |
| `tokenProgram`                | No      | No     | SPL Token Program.                                                                         |
| `systemProgram`               | No      | No     | Solana System Program.                                                                     |

Unlike `buy`, `withdraw` does not require:

* `GlobalStatesPDA`
* Associated Token Program
* Pyth price account
* Platform fee vault

## PDA derivation

### Admin states

```text
["admin-states"]
```

### Bonding curve

```text
["bonding-curve", mint]
```

### Bonding-curve vault

```text
["bonding-curve-vault", mint]
```

### Buyer accumulation

```text
["buyer-accumulation", bondingCurvePda, buyer]
```

The buyer accumulation PDA is tied to both the specific sale and the buyer.

Do not replace `bondingCurvePda` with the mint.

### Buyer token ATA

```text
mint  = token mint
owner = buyer
```

## Withdrawal eligibility

A buyer cannot withdraw while:

```text
isSaleActive == true
```

The instruction performs a lazy expiration check.

If:

```text
isSaleActive == true
isSaleExpired == false
currentTime >= saleExpiresAt
```

the instruction changes the sale state to:

```text
isSaleActive = false
isSaleExpired = true
saleExpiredAt = saleExpiresAt
```

If `saleExpiredAt` has not already been set, the protocol records the configured expiration timestamp rather than the later transaction execution time.

A separate expiration transaction is therefore not required for an expired sale.

## Withdrawal paths

There are two protocol states that allow withdrawal.

### Normal expired sale

The normal path requires:

```text
isSaleActive = false
isSaleExpired = true
isFinalizedSaleCanceled = false
```

The buyer can withdraw.

### Finalized-sale cancellation

A finalized sale can enter the cancellation state.

The cancellation path requires:

```text
isSaleActive = false
isFinalizedSaleCanceled = true
isSaleExpired = false
```

The buyer can then withdraw.

A canceled finalized sale is distinct from a normal expired sale.

The exact on-chain state is authoritative.

## Withdrawal state logic

The protocol first requires:

```text
isSaleActive == false
```

Then it evaluates:

```text
if isFinalizedSaleCanceled:
    require isSaleExpired == false
else:
    require isSaleExpired == true
```

Integrations should read the current `BondingCurvePDA` rather than implementing a simplified eligibility rule.

## Buyer accumulation

The buyer's recorded contribution is stored in:

```rust
pub struct BuyerAccumulationPDA {
    pub total_lamports_contributed: u64,
}
```

The value represents the buyer's cumulative **net SOL contribution after buy fees**.

Example:

```text
Gross buy:   1.000000000 SOL
Buy fee:     0.010000000 SOL
Recorded:    0.990000000 SOL
```

The buy fee is not included in the refundable contribution.

## No withdrawal amount argument

The buyer does not choose a refund amount.

The protocol uses:

```text
BuyerAccumulationPDA.totalLamportsContributed
```

and the currently available SOL in the bonding-curve vault.

This prevents the client from requesting an arbitrary refund amount.

## Vault rent reserve

The bonding-curve vault must retain its required rent-exempt balance.

The protocol calculates the safely available vault balance after the required rent reserve.

The actual refund is limited by both:

```text
recorded contribution
```

and:

```text
available vault balance
```

Therefore:

```text
withdrawAmountInLamports
```

can be lower than:

```text
totalLamportsContributed
```

if the amount safely available from the vault is lower.

Integrations must not assume that the recorded contribution and actual refund are always identical.

## Token burning

Before transferring the SOL refund, the program checks the buyer's token ATA.

If the ATA contains tokens:

1. The buyer must sign.
2. The entire token balance is burned.
3. The token account is reloaded.
4. The resulting balance is checked again.

A successful withdrawal therefore consumes the buyer's remaining RugFreePump sale-token balance.

A custom application must not expect those tokens to remain in the buyer wallet after a successful withdrawal.

## Token ATA closure

After the token balance reaches zero, the buyer token ATA is closed.

The recoverable account balance is returned to the buyer.

The buyer must sign the transaction.

Because `withdraw` expects the buyer ATA to exist, the integration must derive and provide it.

## Buyer accumulation PDA closure

The buyer accumulation account is declared with:

```text
close = buyer
```

After successful withdrawal, the account is closed and its recoverable rent is returned to the buyer.

The account therefore cannot be reused for another purchase in the already non-active sale.

## Transaction costs

The buyer is the transaction payer.

The buyer pays:

* Normal Solana transaction fee
* Any optional priority fee selected by the application

A successful withdrawal may also return recoverable rent from:

* `BuyerAccumulationPDA`
* Buyer token ATA

The exact amounts depend on account balances and current network conditions.

There is no additional RugFreePump buy fee charged by `withdraw`.

## Lazy expiration

A separate expiration transaction is not required.

If:

```text
currentTime >= saleExpiresAt
```

while the sale is still marked active, `withdraw` can perform the expiration transition itself.

When this happens, the program emits:

```text
BondingCurveSaleExpired
```

The event is emitted only when that withdrawal transaction performs the state transition.

If another transaction has already marked the sale expired, a later withdrawal does not emit the expiration event again.

## Anchor example

```ts
import {
  AnchorProvider,
  Idl,
  Program,
} from "@coral-xyz/anchor";

import {
  PublicKey,
  SystemProgram,
} from "@solana/web3.js";

import {
  getAssociatedTokenAddressSync,
  TOKEN_PROGRAM_ID,
} from "@solana/spl-token";

import rugFreePumpIdl from "./rug_free_pump.json";

const PROGRAM_ID = new PublicKey(
  process.env.RUG_FREE_PUMP_PROGRAM_ID!,
);

const provider = new AnchorProvider(
  connection,
  wallet,
  { commitment: "confirmed" },
);

const program = new Program(
  rugFreePumpIdl as Idl,
  provider,
);

const buyer = provider.wallet.publicKey;
const mint = new PublicKey(MINT_ADDRESS);

const [adminStatesPda] =
  PublicKey.findProgramAddressSync(
    [Buffer.from("admin-states")],
    PROGRAM_ID,
  );

const [bondingCurvePda] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("bonding-curve"),
      mint.toBuffer(),
    ],
    PROGRAM_ID,
  );

const [bondingCurveVault] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("bonding-curve-vault"),
      mint.toBuffer(),
    ],
    PROGRAM_ID,
  );

const [buyerAccumulationPda] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("buyer-accumulation"),
      bondingCurvePda.toBuffer(),
      buyer.toBuffer(),
    ],
    PROGRAM_ID,
  );

const buyerAssociatedTokenAccount =
  getAssociatedTokenAddressSync(
    mint,
    buyer,
    false,
    TOKEN_PROGRAM_ID,
  );

const signature =
  await program.methods
    .withdraw()
    .accounts({
      buyer,
      adminStatesPda,
      mint,
      bondingCurvePda,
      bondingCurveVault,
      buyerAccumulationPda,
      buyerAssociatedTokenAccount,
      tokenProgram: TOKEN_PROGRAM_ID,
      systemProgram: SystemProgram.programId,
    })
    .rpc();

console.log(
  "Withdrawal transaction:",
  signature,
);
```

The application should read the current sale and buyer state before constructing the transaction and should verify the resulting state after confirmation.

## Event

A successful withdrawal emits:

```rust
pub struct WithdrawCompleted {
    pub token_mint_address: Pubkey,
    pub withdrawer_address: Pubkey,
    pub withdraw_amount_in_lamports: u64,
    pub is_sale_active: bool,
    pub is_sale_expired: bool,
    pub sale_expired_at: i64,
    pub withdraw_completed_at: i64,
}
```

When `withdraw` performs a lazy expiration transition, the transaction can also emit:

```rust
pub struct BondingCurveSaleExpired {
    pub token_mint_address: Pubkey,
    pub token_creator_address: Pubkey,
    pub total_sold_tokens_e6: u64,
    pub total_raised_usd_e2: u64,
    pub total_collected_buy_fee_in_lamports: u64,
    pub count_of_collected_buy_fee_in_lamports: u64,
    pub total_withdrawable_volume_in_lamports: u64,
    pub is_sale_expired: bool,
    pub sale_expired_at: i64,
}
```

Events are useful for indexing and transaction interpretation, but current account state remains authoritative.

## Important failure conditions

Withdrawal can fail when:

* Platform maintenance mode is enabled.
* The sale is still active.
* The sale is not in a valid expired or finalized-cancellation state.
* The buyer accumulation account is missing or contains no contribution.
* The buyer token ATA does not satisfy the required account constraints.
* Required PDA relationships are invalid.
* Required account ownership or token relationships are invalid.
* The vault does not have sufficient safely available SOL.
* An arithmetic or program validation error occurs.

The exact program error returned by the deployed program is authoritative.

## CPI

`withdraw` is an Anchor program instruction and can be invoked through Solana CPI.

A CPI caller must provide the required accounts and satisfy the same on-chain validation rules.

RugFreePump does not currently provide a maintained CPI wrapper or Rust crate.

A dedicated CPI wrapper and Rust crate are planned as future developer tooling.

## Production integration checklist

Before submitting a production `withdraw` transaction:

* [ ] Use the correct deployment program ID.
* [ ] Use the matching RugFreePump IDL.
* [ ] Derive all required PDAs from the documented seeds.
* [ ] Read current `BondingCurvePDA` state.
* [ ] Read the buyer's `BuyerAccumulationPDA`.
* [ ] Verify the sale is in a withdrawable state.
* [ ] Derive the buyer's token ATA.
* [ ] Use exact integer handling.
* [ ] Sign as the buyer.
* [ ] Confirm the transaction.
* [ ] Verify the resulting account and token state.
