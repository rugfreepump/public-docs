---
title: "Buy"
description: "Integrate directly with the RugFreePump buy instruction to purchase tokens from an active bonding-curve sale."
---

The `buy` instruction purchases tokens from an active RugFreePump bonding-curve sale using SOL.

The instruction accepts a gross SOL amount, deducts the current protocol buy fee, converts the remaining SOL to USD-equivalent value using the verified Pyth SOL/USD price, calculates the token amount from the bonding curve, and transfers the resulting tokens to the buyer.

The transaction is executed entirely on-chain and is atomic under Solana transaction semantics.

## Instruction

```rust
pub fn buy(
    ctx: Context<Buy>,
    lamports_amount: u64,
    expected_total_raised_usd_e2: u64,
    expected_total_sold_tokens_e6: u64,
    slippage_bps: u16,
) -> Result<()>
```

## Arguments

| Argument                        | Type  | Unit         | Description                                                                                             |
| ------------------------------- | ----- | ------------ | ------------------------------------------------------------------------------------------------------- |
| `lamports_amount`               | `u64` | Lamports     | Gross SOL amount submitted by the buyer before the buy fee.                                             |
| `expected_total_raised_usd_e2`  | `u64` | USD e2       | Expected current total USD-equivalent amount raised before the buy.                                     |
| `expected_total_sold_tokens_e6` | `u64` | Token e6     | Expected current total number of tokens sold before the buy.                                            |
| `slippage_bps`                  | `u16` | Basis points | Maximum permitted increase in the bonding curve's average price relative to the expected average price. |

### Integer units

```text
1 SOL = 1,000,000,000 lamports

1 token = 1,000,000 token units

$1.00 = 100 USD e2

$123.45 = 12345 USD e2

10,000 bps = 100%
```

Use exact integer arithmetic.

Do not use JavaScript `number` arithmetic for protocol amounts when precision can be lost.

## Accounts

| Account                       | Mutable | Signer | Derivation / requirement                                                       |
| ----------------------------- | ------- | ------ | ------------------------------------------------------------------------------ |
| `buyer`                       | Yes     | Yes    | Wallet paying SOL and receiving tokens.                                        |
| `mint`                        | Yes     | No     | Token mint being sold. Must match `bondingCurvePda.tokenMintAddress`.          |
| `adminStatesPda`              | No      | No     | PDA: `["admin-states"]`.                                                       |
| `globalStatesPda`             | No      | No     | PDA: `["global-states"]`.                                                      |
| `bondingCurvePda`             | Yes     | No     | PDA: `["bonding-curve", mint]`.                                                |
| `bondingCurveVault`           | Yes     | No     | PDA: `["bonding-curve-vault", mint]`.                                          |
| `associatedBondingCurveAta`   | Yes     | No     | SPL ATA for `mint`, owned by `bondingCurveVault`. Must already exist.          |
| `buyerAccumulationPda`        | Yes     | No     | PDA: `["buyer-accumulation", bondingCurvePda, buyer]`. Created when necessary. |
| `buyerAssociatedTokenAccount` | Yes     | No     | Buyer's ATA for `mint`. Created when necessary.                                |
| `platformFeeVault`            | Yes     | No     | PDA: `["platform-fee-vault"]`.                                                 |
| `solUsdPriceFeed`             | No      | No     | Pyth `PriceUpdateV2` account for the configured SOL/USD feed.                  |
| `tokenProgram`                | No      | No     | SPL Token Program.                                                             |
| `associatedTokenProgram`      | No      | No     | Associated Token Program.                                                      |
| `systemProgram`               | No      | No     | Solana System Program.                                                         |

The buyer is both the transaction payer and required signer.

## PDA derivation

All RugFreePump PDAs use the RugFreePump program ID.

### Admin states

```text
["admin-states"]
```

### Global states

```text
["global-states"]
```

### Bonding curve

```text
["bonding-curve", mint]
```

### Bonding-curve vault

```text
["bonding-curve-vault", mint]
```

### Buyer accumulation

```text
["buyer-accumulation", bondingCurvePda, buyer]
```

The bonding-curve PDA is a seed component.

Do not replace it with the mint.

### Platform fee vault

```text
["platform-fee-vault"]
```

This is the actual vault receiving the buy fee.

It is different from the separate PDA derived using `["platform-fee"]`.

## Associated Token Accounts

### Bonding-curve token ATA

The sale inventory account is the ATA for:

```text
mint  = token mint
owner = bondingCurveVault
```

Because `bondingCurveVault` is a PDA, derive the ATA with off-curve ownership enabled.

```ts
const associatedBondingCurveAta =
  getAssociatedTokenAddressSync(
    mint,
    bondingCurveVault,
    true,
    TOKEN_PROGRAM_ID,
    ASSOCIATED_TOKEN_PROGRAM_ID,
  );
```

### Buyer token ATA

```ts
const buyerAssociatedTokenAccount =
  getAssociatedTokenAddressSync(
    mint,
    buyer,
  );
```

The buyer ATA is automatically initialized by `buy` when it does not already exist.

## Sale-state requirements

A purchase is accepted only while the sale is active.

The program requires:

* Platform maintenance mode is disabled.
* Sale is active.
* Sale is not finalized.
* Finalized-sale cancellation state is not active.
* `lamports_amount > 0`.
* Buyer has sufficient SOL.

The program also checks the sale expiration timestamp.

If the current timestamp has reached `saleExpiresAt`, the program marks the sale inactive and the purchase is rejected.

The on-chain checks are authoritative even if the client performs the same checks before constructing the transaction.

## Buy fee

The gross amount is:

```text
lamports_amount
```

The buy fee rate is read from:

```text
GlobalStatesPDA.buyFeeBps
```

The currently initialized configuration is:

```text
100 bps = 1%
```

The fee is calculated as:

```text
buyFeeLamports =
    lamportsAmount × buyFeeBps / 10,000
```

The net contribution is:

```text
netLamports =
    lamportsAmount - buyFeeLamports
```

The net amount is what enters the bonding-curve purchase calculation.

The current buy fee is configuration state and should be read from `GlobalStatesPDA` rather than permanently hardcoded by an integration.

### Example

With a 1% fee:

```text
Gross:  1.000000000 SOL
Fee:    0.010000000 SOL
Net:    0.990000000 SOL
```

The buyer's refundable contribution is increased by `0.99 SOL`, not `1 SOL`.

## Minimum purchase

The current program constant is:

```text
MIN_BUY_AMOUNT_IN_USD_E2 = 100
```

which represents:

```text
$1.00
```

The check is performed against the buyer's **net USD-equivalent contribution after the buy fee**.

Conceptually:

```text
netUsdE2 =
    netLamports × solUsdPriceE2 / 1,000,000,000
```

The result must satisfy:

```text
netUsdE2 >= 100
```

A gross purchase can therefore fail the minimum requirement after the buy fee is deducted.

## Sale hard cap

The current program constant is:

```text
MAX_USD_RAISE_CAP_IN_USD_E2 = 1,615,000
```

which represents:

```text
$16,150.00
```

The program calculates:

```text
remainingCap =
    1,615,000 - currentTotalRaisedUsdE2
```

The buyer's net USD-equivalent contribution must fit completely inside the remaining capacity.

A purchase that would exceed the hard cap is rejected.

Because the cap check is performed against current on-chain state, clients should refresh the bonding-curve account immediately before constructing the transaction.

## Finalization buffer

The current program constant is:

```text
SALE_FINALIZATION_BUFFER_USD_E2 = 5,000
```

which represents:

```text
$50.00
```

After a successful buy, the program checks the remaining sale capacity.

If:

```text
remainingCap < 5,000
```

the sale is finalized:

```text
isSaleFinalized = true
isSaleActive = false
saleFinalizedAt = current Unix timestamp
```

The final sale total therefore does not necessarily equal exactly `$16,150.00`.

## SOL/USD oracle

The `buy` instruction requires a Pyth `PriceUpdateV2` account.

The current program validates:

1. Full Pyth verification.
2. The expected SOL/USD feed ID.
3. Positive reported price.
4. Confidence no greater than 2% of the reported price.
5. Price update age no greater than 60 seconds.

The current configured SOL/USD feed ID is:

```text
0xef0d8b6fda2ceba41da15d4095d1da392a0d2f8ed0c6c7bc0f4cfac8c280b56d
```

The resulting price is converted to USD e2.

The currently documented Devnet `PriceUpdateV2` account is:

```text
7UVimffxr9ow1uXYxsr4LHAcV58mLzhmwaeKvJ1pjLiE
```

For Mainnet, replace the account with the actual Mainnet `PriceUpdateV2` account configured for the deployed RugFreePump program.

The client must not substitute an arbitrary Pyth price account.

## Slippage protection

RugFreePump's slippage mechanism protects against movement of the bonding curve between quote generation and transaction execution.

The client supplies:

```text
expectedTotalRaisedUsdE2
expectedTotalSoldTokensE6
slippageBps
```

The expected average curve price is:

```text
expectedPriceE2 =
    expectedTotalRaisedUsdE2 × 10^15
    / expectedTotalSoldTokensE6
```

The program calculates the current executed average price:

```text
executedPriceE2 =
    currentTotalRaisedUsdE2 × 10^15
    / currentTotalSoldTokensE6
```

Only an increase is treated as adverse movement:

```text
priceDiff =
    max(executedPriceE2 - expectedPriceE2, 0)
```

Actual slippage is:

```text
actualSlippageBps =
    priceDiff × 10,000 / expectedPriceE2
```

The transaction succeeds only when:

```text
actualSlippageBps <= slippageBps
```

### Required client workflow

Immediately before constructing a `buy` instruction:

```text
BondingCurvePDA.totalRaisedUsdE2
BondingCurvePDA.totalSoldTokensE6
```

must be read from current on-chain state.

Use those values as:

```text
expectedTotalRaisedUsdE2
expectedTotalSoldTokensE6
```

Do not use stale values from an old quote.

If another transaction changes the curve before execution and the resulting price movement exceeds the supplied tolerance, the transaction fails with `SlippageExceeded`.

The initial curve state must also contain a non-zero sold-token value because the protocol's average-price calculation divides by `totalSoldTokensE6`.

## Bonding-curve pricing

The token amount is calculated by the RugFreePump degree-4 polynomial.

The protocol evaluates the cumulative token position at:

```text
startUsd = currentTotalRaisedUsdE2
```

and:

```text
endUsd =
    currentTotalRaisedUsdE2 + netUsdAfterFeeE2
```

The purchased token amount is the difference between those cumulative positions.

The current polynomial coefficients are:

```text
[
  -24,915,010,041,
  109,143,626,050,000,000,
  -186,781,912,610,000,000,000,000,
  171,088,246,150,000,000,000,000,000,000,
  66,288,552,083,000,000,000,000,000,000,000
]
```

with:

```text
scaleFactor = 10^20
```

The implementation evaluates the polynomial using Horner's method and signed 128-bit integer arithmetic.

Conceptually:

```text
F(x) = polynomial(x) / 10^20
```

and:

```text
tokensBought =
    max(F(endUsd) - F(startUsd), 0)
```

The result is expressed in token e6 units.

The on-chain implementation is authoritative.

Integrations that reproduce quotes off-chain must reproduce the integer arithmetic exactly. Floating-point approximations should not be treated as authoritative.

## Token inventory

Before transferring tokens, the program verifies that:

```text
associatedBondingCurveAta.amount >= tokensToBuyE6
```

The account must:

* Exist.
* Use the correct token mint.
* Be owned by the bonding-curve vault PDA.
* Contain sufficient token inventory.

## Transaction execution

A successful buy performs the following logical sequence:

1. Validate maintenance and sale state.
2. Validate the buyer balance.
3. Validate slippage.
4. Validate the Pyth price.
5. Calculate the buy fee.
6. Calculate net USD-equivalent value.
7. Validate the minimum purchase.
8. Validate the sale hard cap.
9. Calculate the token amount.
10. Validate token inventory.
11. Transfer tokens from the bonding-curve token ATA to the buyer ATA.
12. Transfer net SOL from the buyer to the bonding-curve vault.
13. Transfer the buy fee from the buyer to the platform fee vault.
14. Update sale and buyer accounting.
15. Finalize the sale if the finalization condition is reached.
16. Emit events.

Although the token transfer occurs before the SOL transfers in the program, Solana transaction atomicity means a later failure does not leave the earlier successful operations permanently committed.

## Buyer accounting

Each buyer has a:

```rust
BuyerAccumulationPDA
```

with:

```rust
pub struct BuyerAccumulationPDA {
    pub total_lamports_contributed: u64,
}
```

The account allocation is:

```text
8 bytes  Anchor discriminator
8 bytes  total_lamports_contributed
-----------------------------------
16 bytes total
```

The stored value is the buyer's cumulative **net SOL contribution after buy fees**.

Example:

```text
Gross purchase: 1.000000000 SOL
Buy fee:       0.010000000 SOL
Recorded:      0.990000000 SOL
```

This recorded value is subsequently used by `withdraw`.

## Account creation and rent

`buyerAccumulationPda` uses `init_if_needed`.

The buyer is the payer.

The buyer token ATA also uses `init_if_needed`.

Therefore, a first purchase may require the buyer to pay rent for:

* `BuyerAccumulationPDA`
* Buyer token ATA

The buyer also pays the normal transaction fee and any priority fee included by the integrating application.

Later purchases reuse existing accounts.

Query current rent on the target cluster instead of hardcoding a fixed SOL amount.

## Anchor example

The following example demonstrates direct use of the public on-chain interface.

```ts
import { AnchorProvider, BN, Idl, Program } from "@coral-xyz/anchor";
import {
  Connection,
  PublicKey,
} from "@solana/web3.js";
import {
  ASSOCIATED_TOKEN_PROGRAM_ID,
  getAssociatedTokenAddressSync,
  TOKEN_PROGRAM_ID,
} from "@solana/spl-token";

import rugFreePumpIdl from "./rug_free_pump.json";

const PROGRAM_ID = new PublicKey(
  process.env.RUG_FREE_PUMP_PROGRAM_ID!,
);

const SOL_USD_PRICE_FEED_ACCOUNT = new PublicKey(
  process.env.RUG_FREE_PUMP_SOL_USD_PRICE_FEED_ACCOUNT!,
);

const connection = new Connection(
  process.env.SOLANA_RPC_URL!,
  "confirmed",
);

const provider = new AnchorProvider(
  connection,
  wallet,
  { commitment: "confirmed" },
);

const program = new Program(
  rugFreePumpIdl as Idl,
  provider,
);

const buyer = provider.wallet.publicKey;
const mint = new PublicKey(MINT_ADDRESS);

const [adminStatesPda] =
  PublicKey.findProgramAddressSync(
    [Buffer.from("admin-states")],
    PROGRAM_ID,
  );

const [globalStatesPda] =
  PublicKey.findProgramAddressSync(
    [Buffer.from("global-states")],
    PROGRAM_ID,
  );

const [bondingCurvePda] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("bonding-curve"),
      mint.toBuffer(),
    ],
    PROGRAM_ID,
  );

const [bondingCurveVault] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("bonding-curve-vault"),
      mint.toBuffer(),
    ],
    PROGRAM_ID,
  );

const [buyerAccumulationPda] =
  PublicKey.findProgramAddressSync(
    [
      Buffer.from("buyer-accumulation"),
      bondingCurvePda.toBuffer(),
      buyer.toBuffer(),
    ],
    PROGRAM_ID,
  );

const [platformFeeVault] =
  PublicKey.findProgramAddressSync(
    [Buffer.from("platform-fee-vault")],
    PROGRAM_ID,
  );

const associatedBondingCurveAta =
  getAssociatedTokenAddressSync(
    mint,
    bondingCurveVault,
    true,
    TOKEN_PROGRAM_ID,
    ASSOCIATED_TOKEN_PROGRAM_ID,
  );

const buyerAssociatedTokenAccount =
  getAssociatedTokenAddressSync(
    mint,
    buyer,
    false,
    TOKEN_PROGRAM_ID,
    ASSOCIATED_TOKEN_PROGRAM_ID,
  );

// Fetch current state immediately before building the transaction.
const bondingCurve =
  await program.account.bondingCurvePda.fetch(
    bondingCurvePda,
  );

const expectedTotalRaisedUsdE2 =
  new BN(
    bondingCurve.totalRaisedUsdE2.toString(),
  );

const expectedTotalSoldTokensE6 =
  new BN(
    bondingCurve.totalSoldTokensE6.toString(),
  );

const lamportsAmount =
  new BN("100000000"); // 0.1 SOL

const slippageBps =
  new BN("200"); // 2%

const signature =
  await program.methods
    .buy(
      lamportsAmount,
      expectedTotalRaisedUsdE2,
      expectedTotalSoldTokensE6,
      slippageBps,
    )
    .accounts({
      buyer,
      mint,
      adminStatesPda,
      globalStatesPda,
      bondingCurvePda,
      bondingCurveVault,
      associatedBondingCurveAta,
      buyerAccumulationPda,
      buyerAssociatedTokenAccount,
      platformFeeVault,
      solUsdPriceFeed:
        SOL_USD_PRICE_FEED_ACCOUNT,
      tokenProgram: TOKEN_PROGRAM_ID,
      associatedTokenProgram:
        ASSOCIATED_TOKEN_PROGRAM_ID,
      systemProgram:
        SystemProgram.programId,
    })
    .rpc();

console.log("Buy transaction:", signature);
```

The example intentionally reads the bonding-curve state immediately before building the transaction.

The application must provide the correct wallet, RPC endpoint, program ID, IDL, token program constants, and deployment-specific Pyth account.

```ts
      bondingCurvePda,
      bondingCurveVault,
      associatedBondingCurveAta,
      buyerAccumulationPda,
      buyerAssociatedTokenAccount,
      platformFeeVault,
      solUsdPriceFeed:
        SOL_USD_PRICE_FEED_ACCOUNT,
      tokenProgram: TOKEN_PROGRAM_ID,
      associatedTokenProgram:
        ASSOCIATED_TOKEN_PROGRAM_ID,
      systemProgram:
        SystemProgram.programId,
    })

```

This allows the application to add its own:

* Compute-budget instructions
* Priority fee
* Additional application instructions
* Versioned transaction handling
* Custom transaction submission logic

Compute-budget and priority-fee instructions are not part of the RugFreePump `buy` instruction itself.

## Events

A successful purchase emits `BuyCompleted`.

```rust
pub struct BuyCompleted {
    pub token_mint_address: Pubkey,
    pub token_buyer_address: Pubkey,
    pub buy_amount_in_lamports: u64,
    pub buy_amount_in_usd_e2: u64,
    pub buy_amount_in_tokens_e6: u64,
    pub buy_fee_in_lamports: u64,
    pub last_sol_usd_price_e2: u64,
    pub total_sold_tokens_e6: u64,
    pub total_raised_lamports: u64,
    pub total_raised_usd_e2: u64,
    pub total_buy_count: u64,
    pub sale_finalized_at: i64,
    pub is_sale_active: bool,
    pub is_sale_finalized: bool,
    pub is_sale_expired: bool,
    pub buy_completed_at: i64,
}
```

If the purchase finalizes the sale, the program additionally emits:

```rust
pub struct BondingCurveSaleFinalized {
    pub token_mint_address: Pubkey,
    pub token_creator_address: Pubkey,
    pub total_sold_tokens_e6: u64,
    pub total_raised_usd_e2: u64,
    pub total_collected_buy_fee_in_lamports: u64,
    pub count_of_collected_buy_fee_in_lamports: u64,
    pub total_raised_lamports: u64,
    pub total_buy_count: u64,
    pub sale_finalized_at: i64,
}
```

Events are useful for indexing and transaction interpretation.

They should not replace current on-chain account reads when an integration needs authoritative state.

## Important failure conditions

The instruction can fail for conditions including:

```text
PlatformMaintenanceEnabled
SaleNotActive
SaleFinalized
FinalizedSaleAlreadyCanceled
InvalidBuyAmount
InsufficientWalletBalance
IntegerOverflow
SlippageExceeded
UnverifiedPythPriceFeed
InvalidSOLUSDFeedId
OutdatedPriceFeed
InvalidPriceFeed
UnreliablePriceFeed
InvalidBuyFeeRange
BuyAmountTooSmall
SaleCapHasExceeded
ZeroBuyTokenAmount
InsufficientTokenBalance
InvalidBondingCurveVault
InvalidPlatformFeeVault
```

Account constraints can also reject the transaction when supplied accounts do not match the required mint, PDA, ownership, or program relationships.

These errors should be treated as protocol-level transaction failures rather than automatically assuming an RPC or wallet failure.

## CPI

`buy` is an Anchor program instruction and can be invoked through Solana CPI.

A CPI caller must provide the same required accounts and satisfy the same on-chain validation rules.

RugFreePump does not currently provide a maintained CPI wrapper or Rust crate.

A dedicated CPI wrapper and Rust crate are planned as future developer tooling.

## Production integration checklist

Before submitting a production `buy` transaction:

* [ ] Use the correct deployment program ID.
* [ ] Use the matching RugFreePump IDL.
* [ ] Derive all PDAs from the documented seeds.
* [ ] Read fresh `BondingCurvePDA` state.
* [ ] Use exact integer arithmetic.
* [ ] Supply the correct Pyth `PriceUpdateV2` account.
* [ ] Read the current `buyFeeBps`.
* [ ] Account for the net amount after the buy fee.
* [ ] Check the buyer's available SOL.
* [ ] Account for possible account-creation rent.
* [ ] Select an appropriate slippage tolerance.
* [ ] Submit promptly after building the transaction.
* [ ] Handle stale blockhashes and transaction failures.
* [ ] Confirm the transaction.
* [ ] Refresh on-chain state after confirmation.
* [ ] Use emitted events as transaction signals, not as a replacement for authoritative account state.
