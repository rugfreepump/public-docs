RugFreePump exposes its protocol through a Solana program and its on-chain accounts.

Developers can build applications, integrations, automation, analytics systems, trading tools, and other on-chain programs directly on top of the RugFreePump protocol using standard Solana tooling and the published Anchor interface.

The documented developer integration surface is intentionally on-chain first. RugFreePump's hosted application and internal backend infrastructure are application infrastructure and are not required dependencies for protocol integrations.

## Supported integration surface

The Developer Guide currently documents two public protocol instructions for direct developer integration:

| Instruction | Purpose                                                                     |
| ----------- | --------------------------------------------------------------------------- |
| `buy`       | Purchase tokens from an active bonding-curve sale using SOL.                |
| `withdraw`  | Redeem a buyer's recorded contribution after the sale becomes withdrawable. |

These instructions are Anchor program instructions and can be constructed using the published IDL and standard Solana tooling.

The protocol's on-chain program remains the authoritative source for account state, sale state, configuration used by each instruction, and transaction validation.

## Deployment configuration

Always use the program ID and protocol accounts corresponding to the Solana environment being targeted.

### Devnet

The currently documented Devnet deployment uses:

```text
RugFreePump program:
9hpBPEiywp7FPAq5uP253eAZzdJ1Cpd36L5RAYuc9xSw

SOL/USD PriceUpdateV2 account:
7UVimffxr9ow1uXYxsr4LHAcV58mLzhmwaeKvJ1pjLiE
```

### Mainnet

Mainnet addresses must be replaced with the actual deployment values before production use:

```text
RugFreePump program:
REPLACE_WITH_MAINNET_RUG_FREE_PUMP_PROGRAM_ID

SOL/USD PriceUpdateV2 account:
REPLACE_WITH_MAINNET_SOL_USD_PRICE_FEED_ACCOUNT
```

Do not derive or reuse the RugFreePump Devnet program ID for Mainnet.

For production integrations, keep deployment-specific values in configuration rather than embedding them throughout application code.

For example:

```ts
import { PublicKey } from "@solana/web3.js";

export const RUG_FREE_PUMP_PROGRAM_ID = new PublicKey(
  process.env.RUG_FREE_PUMP_PROGRAM_ID!,
);

export const SOL_USD_PRICE_FEED_ACCOUNT = new PublicKey(
  process.env.RUG_FREE_PUMP_SOL_USD_PRICE_FEED_ACCOUNT!,
);
```

The canonical Solana System Program, SPL Token Program, and Associated Token Program addresses are network-independent.

## On-chain state is authoritative

The RugFreePump program and its Solana accounts are the authoritative source of protocol state.

Off-chain applications may index, cache, transform, or display protocol information, but those services do not replace the underlying on-chain state.

For protocol-critical operations, integrations should:

1. Read the relevant on-chain accounts.
2. Derive required PDAs from the documented seeds.
3. Construct instructions from current state.
4. Sign using the required wallet.
5. Submit and confirm the transaction.
6. Read the resulting state or transaction data after confirmation.

Do not treat a cached API response, previously calculated quote, or internal application state as authoritative when constructing a protocol transaction.

## Core units

RugFreePump uses integer-scaled values for protocol accounting.

| Value                 | Unit         | Scale                            |
| --------------------- | ------------ | -------------------------------- |
| SOL                   | Lamports     | `1 SOL = 1,000,000,000` lamports |
| Token amounts         | Token e6     | `1 token = 1,000,000` units      |
| USD-equivalent values | USD e2       | `$1.00 = 100`                    |
| Prices                | USD e2       | `$123.45 = 12345`                |
| Fees and percentages  | Basis points | `10,000 = 100%`                  |
| Timestamps            | Unix seconds | Integer seconds                  |

Use exact integer arithmetic for these values.

For TypeScript applications, prefer `BN`, `bigint`, or another exact integer representation instead of JavaScript floating-point arithmetic.

## Bonding-curve model

RugFreePump uses SOL as the asset contributed by buyers while the bonding-curve calculation uses USD-equivalent value.

The `buy` instruction:

1. Receives a gross SOL amount in lamports.
2. Reads and validates the configured Pyth SOL/USD price.
3. Calculates the protocol buy fee.
4. Converts the remaining SOL to USD-equivalent value.
5. Checks the minimum purchase and remaining sale capacity.
6. Calculates the token amount using the on-chain bonding-curve function.
7. Transfers tokens to the buyer.
8. Transfers net SOL to the bonding-curve vault.
9. Transfers the buy fee to the platform fee vault.
10. Updates bonding-curve and buyer accounting.

The buyer's recorded refundable contribution is the **net SOL contribution after the buy fee**, not the gross amount supplied to `buy`.

See [Buy](./on-chain-integration/buy) for the complete instruction reference.

## Protocol accounts and PDAs

All RugFreePump PDAs are derived using the RugFreePump program ID.

### Admin states

```text
["admin-states"]
```

Used by both supported instructions to validate platform maintenance state.

### Global states

```text
["global-states"]
```

Contains protocol-wide state used by the `buy` instruction, including the current buy fee configuration.

### Bonding curve

For token mint `M`:

```text
["bonding-curve", M]
```

The resulting account stores the sale's bonding-curve state and accounting.

### Bonding-curve vault

For token mint `M`:

```text
["bonding-curve-vault", M]
```

This PDA holds the SOL associated with the bonding-curve sale and is also the authority of the bonding-curve token ATA.

### Buyer accumulation

For bonding-curve PDA `C` and buyer wallet `B`:

```text
["buyer-accumulation", C, B]
```

The bonding-curve PDA is part of the seed.

Do not substitute the token mint directly for the bonding-curve PDA.

The account stores the buyer's cumulative net SOL contribution for that sale.

### Platform fee vault

The platform fee vault used by `buy` is derived from:

```text
["platform-fee-vault"]
```

This is the account receiving the buy fee.

Do not confuse this account with the separate platform-fee PDA derived from:

```text
["platform-fee"]
```

The two addresses have different seeds and serve different purposes.

## Associated Token Accounts

The supported instructions use standard SPL Associated Token Accounts.

### Buyer token ATA

```text
mint  = token mint
owner = buyer wallet
```

For `buy`, the ATA is initialized automatically if required.

For `withdraw`, the ATA must already exist because the instruction operates on the buyer's existing token account.

### Bonding-curve token ATA

```text
mint  = token mint
owner = bonding-curve vault PDA
```

Because the owner is a PDA, clients deriving this ATA must allow an off-curve owner.

Example:

```ts
import {
  getAssociatedTokenAddressSync,
  TOKEN_PROGRAM_ID,
  ASSOCIATED_TOKEN_PROGRAM_ID,
} from "@solana/spl-token";

const bondingCurveTokenAta = getAssociatedTokenAddressSync(
  mint,
  bondingCurveVault,
  true,
  TOKEN_PROGRAM_ID,
  ASSOCIATED_TOKEN_PROGRAM_ID,
);
```

## Direct integration workflow

A production integration should generally follow this sequence.

### 1. Load the correct program interface

Use the IDL corresponding to the exact RugFreePump deployment being integrated.

See [Anchor IDL & Types](./anchor-idl-and-types/usage).

### 2. Configure the target environment

Verify:

* Solana cluster
* RugFreePump program ID
* RugFreePump IDL version
* Pyth SOL/USD account
* SPL program addresses
* Any other accounts required by the instruction

### 3. Derive protocol accounts

Derive the required PDAs using the exact seeds documented for the instruction.

### 4. Read current state

Read the relevant protocol accounts immediately before constructing state-sensitive transactions.

For `buy`, this includes the current `BondingCurvePDA` because its state is used directly by the slippage mechanism.

For `withdraw`, read the current `BondingCurvePDA` and the buyer's `BuyerAccumulationPDA`.

### 5. Construct the instruction

Build the instruction using:

* Correct program ID
* Correct accounts
* Correct PDA derivations
* Correct integer units
* Current protocol state
* Required oracle account
* Appropriate slippage values for `buy`

### 6. Build and sign the transaction

For both supported instructions:

```text
buyer = transaction payer + required signer
```

The RugFreePump program does not require custody of the buyer's private key.

### 7. Simulate and submit

Where appropriate, simulate before submission and handle:

* Blockhash expiration
* RPC failures
* Account validation failures
* Protocol validation failures
* Slippage failures
* Insufficient balance
* Oracle failures

### 8. Confirm and verify

After confirmation, read the relevant account state and/or transaction events.

A submitted transaction should not be treated as proof of the expected protocol state until confirmation and verification have completed.

## State freshness

Solana state can change between transaction construction and execution.

This is particularly important for `buy`.

A production client should:

1. Fetch the current `BondingCurvePDA`.
2. Read `totalRaisedUsdE2`.
3. Read `totalSoldTokensE6`.
4. Use those values as the expected state supplied to `buy`.
5. Construct and submit the transaction promptly.
6. Handle `SlippageExceeded` by refreshing state and rebuilding the transaction.

Do not reuse a stale quote indefinitely.

## Transaction costs and rent

RugFreePump transactions are subject to normal Solana network costs.

Depending on the instruction and account state, the buyer may need to pay:

* Solana transaction fees
* Optional priority fees
* Rent for accounts created by the transaction

For `buy`, the buyer pays for accounts initialized by the instruction when they do not already exist:

* `BuyerAccumulationPDA`
* Buyer's token ATA

Exact rent and transaction fees depend on the target cluster and current network state. Query current values rather than hardcoding them.

A successful `withdraw` may return rent from accounts that are closed during the instruction.

## Cross-program invocation

The public RugFreePump instructions are Anchor program entry points and can be invoked by other Solana programs through CPI.

A CPI caller must satisfy the same validation rules enforced by the target instruction, including:

* Account relationships
* PDA derivations
* Signer requirements
* Account ownership
* Sale state
* Maintenance state
* Oracle validation
* Slippage requirements
* Token account requirements
* Instruction-specific validation

RugFreePump does not currently provide a maintained CPI wrapper or Rust integration crate.

A dedicated CPI wrapper and Rust crate are planned as future developer tooling.

## Application boundary

The public integration boundary is the RugFreePump on-chain program.

The following internal application components are not required protocol interfaces:

* RugFreePump backend classes
* Internal HTTP endpoints
* Internal database schemas
* Internal WebSocket topics
* Internal transaction builders
* Internal metadata-processing services
* Internal RPC infrastructure

These systems may change independently of the on-chain protocol interface.

## Version compatibility

The IDL, generated types, program ID, and deployed program must correspond to the same protocol version.

When upgrading an integration:

1. Confirm the target program ID.
2. Obtain the corresponding IDL.
3. Update generated types.
4. Revalidate PDA derivation.
5. Revalidate instruction accounts and arguments.
6. Re-test transaction construction.
7. Re-test event decoding.
8. Revalidate configuration assumptions.

The deployed on-chain program and its documented interface define the protocol compatibility boundary.
