The RugFreePump protocol's core functionality is exposed through its deployed Solana program. Developers can integrate directly with the program using Solana RPC, the RugFreePump Anchor IDL, generated types, and standard Solana and Anchor tooling.

The RugFreePump program is deployed and callable on Solana, while its underlying source code is not part of the public developer interface. The documented IDL, generated types, accounts, seeds, instruction interfaces, and protocol behavior provide the information required for direct integration.

RugFreePump's hosted application and backend services support the platform itself, but they are not required interfaces for protocol integrations.

## Integration model

The primary integration surface is the RugFreePump on-chain program.

Developers can interact directly with the program's documented instructions and accounts using standard Solana tooling. This includes client applications, automated systems, analytics, wallets, and other Solana programs, without requiring access to RugFreePump's hosted application or backend services.

RugFreePump does not currently provide a public off-chain SDK or developer HTTP API. Direct integrations therefore interact with Solana and the deployed RugFreePump program directly.

The public program instructions can also be invoked by other Solana programs through cross-program invocation (CPI), subject to the accounts, signer requirements, state conditions, and validation enforced by each instruction.

A maintained CPI wrapper and Rust crate are planned as future developer tooling for program-to-program integrations.

## Public program interface

The current RugFreePump program exposes four public instructions:

| Instruction         | Purpose                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `create_pool`       | Creates and initializes a token sale and its bonding-curve state.                          |
| `buy`               | Purchases tokens from an active bonding-curve sale using SOL.                              |
| `withdraw`          | Burns a buyer's purchased tokens and refunds the buyer when the sale becomes withdrawable. |
| `migrate_liquidity` | Processes a finalized sale and migrates liquidity through the configured DEX integration.  |

All four are Anchor program instructions.

The current Developer Guide provides detailed integration references for `buy` and `withdraw`. The instruction reference pages document the accounts, PDA derivation, arguments, units, state requirements, transaction behavior, fees, events, and important validation rules required to construct those instructions correctly.

## Protocol state

The RugFreePump on-chain program and its Solana accounts are the authoritative source of protocol state.

The hosted RugFreePump application and supporting off-chain services may index, cache, transform, or display protocol information, but those services are not replacements for the underlying on-chain state.

For protocol-critical operations, integrations should read the relevant on-chain accounts and construct transactions using current protocol state.

This is particularly important for state that can change between transaction construction and execution, including bonding-curve state, sale lifecycle state, and protocol configuration.

## Core units

RugFreePump uses integer representations for protocol values rather than floating-point values.

| Value                  | Unit             | Scale                            |
| ---------------------- | ---------------- | -------------------------------- |
| SOL amounts            | Lamports         | `1 SOL = 1,000,000,000` lamports |
| Token amounts          | Token base units | `1 token = 1,000,000` units      |
| USD-equivalent amounts | USD e2           | `$1.00 = 100`                    |
| Prices                 | USD e2           | `$123.45 = 12345`                |
| Percentages and fees   | Basis points     | `10000 = 100%`                   |
| Timestamps             | Unix seconds     | Integer seconds                  |

When constructing instructions or processing account data, preserve these integer representations. Avoid unnecessary conversion to JavaScript floating-point numbers, particularly for token amounts, SOL amounts, and protocol accounting values.

## Bonding-curve model

RugFreePump uses SOL as the asset contributed by buyers while the bonding-curve calculation is denominated in USD-equivalent value.

The `buy` instruction uses the current verified SOL/USD oracle price to convert the buyer's net SOL contribution into USD-equivalent value for the bonding-curve calculation.

At a high level, the buy flow is:

1. The buyer supplies a SOL amount in lamports.
2. The program verifies the supplied SOL/USD Pyth price account.
3. The configured buy fee is deducted.
4. The remaining SOL is converted to USD-equivalent value.
5. The net USD-equivalent amount is checked against the protocol's purchase limits.
6. The bonding-curve pricing function determines the token amount.
7. Tokens are transferred from the bonding-curve token account to the buyer.
8. Net SOL is transferred to the bonding-curve vault.
9. The buy fee is transferred to the platform fee vault.
10. Bonding-curve accounting is updated.

The buyer's recorded refundable contribution is based on the **net SOL contribution after the buy fee**, not the gross SOL amount supplied to `buy`.

The exact purchase calculation and its validation rules are documented on the [Buy](../on-chain-integration/buy) reference page.

## Protocol accounts and PDAs

RugFreePump uses deterministic program-derived addresses (PDAs) for its protocol state and vault accounts.

### Program-level PDAs

| Account                | Seeds                    |
| ---------------------- | ------------------------ |
| Mint authority         | `["mint-authority"]`     |
| Admin states           | `["admin-states"]`       |
| Global states          | `["global-states"]`      |
| Platform fee vault PDA | `["platform-fee"]`       |
| Platform fee vault     | `["platform-fee-vault"]` |

The two platform-fee-related accounts are different accounts and use different seeds.

### Per-token PDAs

For a token mint `M`:

| Account                 | Seeds                        |
| ----------------------- | ---------------------------- |
| Bonding curve           | `["bonding-curve", M]`       |
| Bonding-curve SOL vault | `["bonding-curve-vault", M]` |

### Buyer accumulation PDA

For buyer `B` and bonding-curve PDA `C`:

```text
["buyer-accumulation", C, B]
```

The bonding-curve PDA is used as a seed component rather than the token mint directly.

The buyer accumulation account records the buyer's cumulative net SOL contribution for that sale.

### Associated token accounts

The protocol uses standard SPL Associated Token Accounts for token balances:

* Buyer token account: `(mint, buyer)`
* Bonding-curve token account: `(mint, bondingCurveVault)`

Because the bonding-curve vault is a PDA, integrations deriving its associated token account must allow an off-curve owner.

Instruction-specific account requirements take precedence over this general reference. See the individual instruction pages for the complete account lists.

## Direct integration workflow

A direct integration generally follows these steps.

### 1. Load the program interface

Use the RugFreePump Anchor IDL and generated types corresponding to the deployed program version.

See [Anchor IDL & Types](../anchor-idl-and-types/usage).

### 2. Derive required accounts

Derive the PDAs and associated token accounts required by the instruction using their documented seeds and derivation rules.

### 3. Read current on-chain state

Fetch the accounts required to understand the current protocol state.

Depending on the instruction, this can include:

* `AdminStatesPDA`
* `GlobalStatesPDA`
* `BondingCurvePDA`
* `BuyerAccumulationPDA`
* SPL token accounts
* The required oracle account

### 4. Construct the instruction

Build the instruction using:

* The current account addresses
* Correct PDA derivations
* Correct integer units
* Current protocol state
* Instruction arguments
* Required oracle accounts
* Required slippage parameters where applicable

### 5. Build and sign the transaction

Construct a Solana transaction containing the instruction and have the required signer authorize it.

For `buy` and `withdraw`, the buyer is the required transaction signer and payer.

### 6. Submit and confirm

Submit the transaction through the Solana network and handle normal transaction conditions such as blockhash expiration, RPC errors, simulation failures, and on-chain validation failures.

### 7. Verify resulting state

After confirmation, read the relevant on-chain accounts or transaction data to verify the resulting protocol state.

Do not treat transaction submission alone as confirmation that an expected protocol state was established.

## State freshness and transaction construction

On-chain state can change between reading an account and executing a transaction.

This is particularly important for `buy`, where the instruction includes expected bonding-curve state values as part of its slippage protection.

A direct integration should therefore:

1. Read the current bonding-curve state.
2. Use the current state to construct the expected values required by `buy`.
3. Construct and submit the transaction promptly.
4. Handle slippage failures when the on-chain state has moved beyond the accepted tolerance.

A transaction constructed from stale bonding-curve state may fail even when the underlying sale remains active.

The complete slippage calculation and required `buy` arguments are documented in the [Buy](../on-chain-integration/buy) reference.

## Transaction costs and account creation

RugFreePump transactions remain subject to normal Solana network costs.

Depending on the instruction and account state, an integration may need to account for:

* Solana transaction fees
* Optional priority fees
* Rent required when new accounts are created

For `buy`, the buyer is the payer for accounts initialized by the instruction. This can include:

* `BuyerAccumulationPDA`
* The buyer's associated token account

Exact transaction fees and account-rent requirements depend on the Solana cluster and current network state. Integrations should query current values rather than hardcode them.

## Cross-program invocation

The public RugFreePump instructions are Anchor program entry points and can be invoked by other Solana programs through CPI.

A CPI caller must satisfy the same protocol requirements enforced by the target instruction, including the following:

* Accounts
* PDA derivations
* Signer requirements
* Account ownership and constraints
* Sale lifecycle state
* Maintenance state
* Oracle validation
* Slippage conditions
* Token account requirements
* Instruction-specific validation

RugFreePump does not currently provide a maintained CPI wrapper or Rust crate.

A dedicated CPI wrapper and Rust crate are planned as future developer tooling. Such tooling will simplify program-to-program integration but will not change the underlying on-chain program interface or its validation rules.

## Interface boundaries

The deployed RugFreePump program is the protocol integration boundary.

RugFreePump's hosted application and backend infrastructure may provide application-level functionality such as transaction preparation, indexing, metadata processing, analytics, and real-time updates. These services are not required to interact with the protocol directly.

Developers should not depend on undocumented application internals as part of a protocol integration.

The following are not part of the documented protocol interface:

* Internal backend implementations
* Internal transaction-building code
* Internal database schemas
* Undocumented API routes
* Internal WebSocket infrastructure
* Internal metadata-processing implementation
* Internal RPC infrastructure

These implementation details may change independently of the on-chain protocol interface.

## Version compatibility

The Anchor IDL describes a specific version of the RugFreePump program interface.

When integrating:

* Use the IDL corresponding to the deployed program version.
* Verify the program ID for the target environment.
* Use the documented account and instruction definitions for that version.
* Read protocol configuration from on-chain state where applicable rather than assuming that configuration values are permanent.
* Revalidate account and instruction requirements when updating an integration.

The deployed on-chain program and its documented interface define the compatibility boundary for protocol integrations.
