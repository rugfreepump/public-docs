---
title: "Developer limitations"
description: "Understand the current scope, responsibilities, and supported integration model for RugFreePump developers."
---

RugFreePump is an on-chain token launch protocol.

Its public developer integration boundary is the RugFreePump Solana program and the accounts, instructions, events, PDAs, and configuration required by that program.

The protocol does not require developers to depend on RugFreePump's hosted application or internal backend infrastructure.

## Current developer interface

The currently documented direct integration surface consists of:

* RugFreePump's Solana program
* `buy`
* `withdraw`
* Protocol accounts
* Program Derived Addresses
* SPL Token accounts
* Program events
* Anchor IDL
* Generated TypeScript types
* Standard Solana RPC access

The Developer Guide focuses on `buy` and `withdraw` as the supported direct developer integration paths.

## No public off-chain SDK

RugFreePump does not currently provide an official off-chain SDK.

An off-chain SDK is not required to integrate with the protocol.

Developers can use standard Solana tooling such as:

* Anchor
* Solana Web3.js
* SPL Token libraries
* Direct Solana instruction construction
* Their own RPC infrastructure

The published Anchor IDL and generated TypeScript types provide the interface required for standard Anchor-based integrations.

## No public developer HTTP API

RugFreePump does not currently provide a dedicated public developer HTTP API.

The hosted RugFreePump application may use backend services for:

* User interface functionality
* Indexing
* Metadata processing
* Transaction preparation
* Analytics
* Real-time updates

These services are application infrastructure rather than protocol interfaces.

Developers building protocol integrations should read protocol state from Solana and submit protocol instructions directly.

## No dedicated hosted developer service

RugFreePump does not currently operate a separate managed developer platform providing:

* Developer API keys
* Hosted transaction relaying
* Dedicated quote services
* Hosted indexing APIs
* Managed trading infrastructure

Direct integrators are responsible for selecting the infrastructure appropriate for their applications.

Depending on the integration, this includes:

* Solana RPC access
* Wallet and signing infrastructure
* Transaction construction
* Transaction simulation
* Transaction submission
* Retry handling
* Blockhash management
* State refresh
* Application-specific indexing
* Monitoring

## Direct integration responsibilities

Applications integrating directly with RugFreePump are responsible for correctly handling:

* Program ID
* Target Solana cluster
* IDL version
* PDA derivation
* Account relationships
* Instruction arguments
* Integer units
* Protocol configuration
* Sale lifecycle state
* Slippage
* Oracle requirements
* Transaction fees
* Account creation
* Transaction confirmation

The on-chain program remains authoritative when application state differs from cached or indexed information.

## Wallet and signing responsibility

For the supported `buy` and `withdraw` instructions:

```text
buyer = transaction payer + required signer
```

RugFreePump does not require custody of the buyer's wallet keys.

Applications are responsible for:

* Wallet connection
* Transaction presentation
* User authorization
* Signing
* Submission
* Confirmation
* Application-level transaction state

## State and quote responsibility

On-chain state can change between transactions.

Applications constructing `buy` transactions are responsible for:

* Fetching current bonding-curve state
* Creating fresh quotes
* Selecting appropriate slippage
* Rebuilding stale transactions
* Handling `SlippageExceeded`
* Refreshing state after confirmation

A previously calculated quote should not be treated as permanently valid.

## Protocol configuration

Protocol configuration must be interpreted according to the instruction consuming it.

For example, the `buy` instruction reads:

```text
GlobalStatesPDA.buyFeeBps
```

for the current buy fee.

Other purchase constraints, including the current minimum buy amount and maximum USD-equivalent raise cap, are enforced by program constants in the current on-chain implementation.

Developers should therefore refer to the specific instruction reference rather than assuming that every configuration-looking field is dynamically consumed by every instruction.

## Deployment responsibility

Program IDs and deployment-specific external accounts must be verified for the target environment.

Developers must confirm:

* RugFreePump program ID
* Solana cluster
* Pyth SOL/USD `PriceUpdateV2` account
* Matching RugFreePump IDL
* SPL program addresses
* Any other required external program accounts

The currently documented Devnet RugFreePump program is:

```text
9hpBPEiywp7FPAq5uP253eAZzdJ1Cpd36L5RAYuc9xSw
```

Mainnet deployment values must be replaced with the actual production deployment values.

Do not copy Devnet-specific RugFreePump or Pyth accounts into Mainnet integrations without verification.

## Internal RugFreePump infrastructure

RugFreePump's internal application infrastructure may construct transactions or provide application functionality.

Those implementation details are not guaranteed developer interfaces.

Production integrations should not depend on undocumented:

* Backend classes
* Database schemas
* Internal HTTP endpoints
* Internal WebSocket topics
* Internal transaction-builder functions
* Internal RPC configuration
* Internal metadata-processing behavior

These systems may change independently of the on-chain protocol interface.

## RPC responsibility

Direct integrations must provide their own Solana RPC access.

An application may use any RPC provider or infrastructure that supports the target Solana environment and provides the reliability and performance appropriate for its workload.

RugFreePump's internal RPC infrastructure is not a required dependency.

## CPI support

RugFreePump's public Anchor instructions can be invoked through Solana CPI.

A separate CPI wrapper is not required for the underlying program to be CPI-compatible.

However, RugFreePump does not currently provide a maintained official CPI wrapper or Rust integration crate.

A dedicated CPI wrapper and Rust crate are planned as future developer tooling.

Until those artifacts are available, program-to-program integrations must construct the CPI invocation against the public on-chain instruction interface and satisfy its account and signer requirements directly.

## Future developer tooling

The planned official developer tooling is intentionally focused on on-chain integration:

* CPI wrapper
* Rust integration crate

These tools are intended to reduce integration complexity without introducing a dependency on a hosted off-chain API.

No commitment is made here to provide a separate off-chain SDK, developer API, or managed developer service.

## Compatibility expectations

The public on-chain program is the primary compatibility boundary.

Developers should:

* Pin or track the program version they integrate with.
* Keep the corresponding IDL available.
* Regenerate types when the program interface changes.
* Validate account layouts and instruction requirements when upgrading.
* Avoid undocumented application internals.
* Test transactions against the intended Solana environment.

An internal RugFreePump service changing does not necessarily imply an on-chain protocol change.

Likewise, an on-chain program change should not be inferred solely from an internal application change.

## Support scope

The Developer Guide documents the public protocol interface and expected integration behavior.

Integrators remain responsible for their own application architecture and infrastructure.

RugFreePump does not guarantee operation or maintenance of third-party:

* RPC infrastructure
* Wallet integrations
* Bots
* Analytics systems
* Trading applications
* Custom frontends
* Indexers
* Transaction relayers

The public on-chain interface remains the foundation for these integrations.

## Recommended integration boundary

For long-term integrations, the intended architecture is:

```text
Your Application
       |
       v
Your Solana RPC
       |
       v
RugFreePump On-Chain Program
       |
       +--> Protocol Accounts
       +--> SPL Token Accounts
       +--> Pyth
```

Applications should avoid making internal RugFreePump infrastructure a mandatory dependency unless a future official developer product explicitly documents it as part of the public integration surface.

## Before production deployment

Before releasing a production RugFreePump integration:

* [ ] Confirm the target cluster.
* [ ] Confirm the production RugFreePump program ID.
* [ ] Obtain the matching IDL.
* [ ] Regenerate or update generated types.
* [ ] Confirm the production Pyth SOL/USD account.
* [ ] Verify all PDA derivations.
* [ ] Verify all account relationships.
* [ ] Verify instruction arguments and units.
* [ ] Test transaction construction.
* [ ] Test simulation and failure handling.
* [ ] Test transaction confirmation.
* [ ] Test state refresh after successful transactions.
* [ ] Remove all Devnet-specific configuration.
* [ ] Avoid dependencies on undocumented RugFreePump backend services.
